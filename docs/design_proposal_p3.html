Proposed direction

Three details that earn their place.

01 / Motion

One motion language.

Open toward the point of origin. Settle once. Keep every control available as soon as the window appears.

  • Docked: a 200 ms reveal from the upper edge; close in about 140 ms.
  • Floating: an 8 px lift with a short fade. Preserve the saved position.
  • Menus: 5 px travel, 130–160 ms; no bounce or stagger.
  • A repeated hotkey reverses the current movement. Dragging or resizing settles it immediately.
Propose for P3
02 / Loading

Let the useful page through.

Keep live pages intact. For a new visit, show a quiet site identity and offer “Show page” before the long-wait timeout.

  • Try exposing the native page at DOMContentLoaded, while navigation continues. Validate usability on real sites.
  • A thin indeterminate line means loading; it never invents a percentage.
  • Fast returns get no spinner or minimum display time.
  • Slow and failed visits have distinct messages. Never reload a draft automatically.
Prototype, then validate
03 / Character

A companion in the margin.

A small ember with warm eyes in the existing 30 × 30 slot. A soft body, a tiny spark, and a little personality.

  • A small local gaze, limited to a few pixels while the window is visible.
  • A blink and gentle tilt on hover; a brief hop when greeted. Clicking has no application action.
  • No idle loop, page reading, generation detection, or notification badge.
  • Optional; the slot stays the same size when disabled. Reduced motion keeps the face static.
Selected for P3
Loading / research shortlist

Fewer obstacles between you and a page.

IdeaExpected benefitRecommendation
Browser HTTP cacheReuse eligible scripts, styles and images across visits.Verify persistent profile behavior and response headers first. Leave revalidation to WebView2. No routine cache clearing.
Saved page HTMLCan display an old shell, but cannot restore a running application.Defer. For authenticated apps, HTML omits live JS state and still needs APIs; stale markup can conflict with new assets. Keep the actual live page instead.
Ads and tracker filteringPotentially fewer requests on ad-heavy sites. Benefit on AI sites is unproven.Separate experiment. Opt in per site, with a visible “Pause for this site”. Compare loading, login, upload and streaming with filtering off/on.
Clean copied linksCleaner sharing; possible removal of known tracking parameters.Start with an explicit copy action. Preserve the open URL, path, hash, auth tokens and signatures. URL cleanup alone is not a speed improvement.
Warm one favorite siteMay shorten the first visit after launch, at the cost of startup work and memory.Optional later experiment, never prefetch every site or follow hover automatically. Keep the existing lazy session model as the default.
Extensions / separate compatibility experiment

A small shortlist, with a reason for each.

A / First candidate

uBlock Origin Lite

A candidate for optional network filtering. Check WebView2 API support, rule application, per-site exceptions, updates and licensing before any integration.

Not tested in Spark
B / Useful on demand

Reader view / translation

Useful for articles and documentation. Prefer explicit “Read” or “Translate” actions; keep interactive AI pages intact. Validate an extension before choosing a specific package.

Explore after core polish
C / Keep the palette intact

Automatic darkening

Defer extensions that restyle every page. They can change brand colors, contrast and layout. Spark currently has one graphite shell; a light theme is a separate design scope.

Defer for this iteration

WebView2 has a native API for loading unpacked extensions, but no standard browser toolbar to host their buttons and popups. Spark would need native bridge work and its own entry points. This preview does not load extensions, block requests, accelerate a real website, or prove native animation quality.

Technical references: WebView2 extension API and UI limitations · Performance guidance · Request filtering · Profile storage · uBlock Origin Lite.
